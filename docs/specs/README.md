# accord の要件

## この置き場は何か

accord が外から見て何をするかを、機械で確かめられる形で 1 件 1 文に書いたものを、この置き場に集めます。要件 1 件は番号を持ち、その番号を名前に持つテストと結びます。人の記憶ではなく文字列の一致で結ぶので、要件だけが増えてテストが無い状態や、もう無い要件をテストが指したままの状態を、機械が見つけます。

要件は機能ごとのファイルにあります。いまあるのは、整合の検査と、正本の読み方の設定と、文面の材料の取り出しと、機能の登記とパッケージの改訂と、決めの読み書きと、公開記録の登記と、ID で結ぶことと、書きの守りです。全部を一度に書き起こさず、次に触る機能から順に 1 つずつ書き足していきます。

## 何を要件にするか

要件にするのは、機械検査で確かめられる振る舞いだけです。人が読んで判断する条件（説明の分かりやすさ、設計の筋のよさ）は要件にしません。

先に要件を書くのは、次の 4 つのときです。

- 新しい機能を足すとき
- 外から見える振る舞いを変えるとき
- 利用者に返る文言を変えるとき
- 依存するパッケージの版を上げるとき

外すのは、コメントの修正と、外から見えない内部の名前の直しです。

## ファイルの名前

要件は `docs/specs/<機能名>.md` に書きます。機能名は英小文字とハイフンだけを使います。この `README.md` は案内なので、要件は置きません（検査もこのファイルを読みません）。

要件のファイルの先頭には、機能の名前を題（`# ` の見出し）として 1 つ置きます。検査が要件として読むのは、`REQ-` で始まる見出しだけです。

## 番号の振り方

番号は `REQ-014` の形の 3 桁の連番です。この番号のことを、以下では要件の番号と呼びます。正本の項目に人が振る ID（職歴や機能に付ける短い名前。リポジトリ直下の `README.md` の「データの型とルール」）とは別のもので、混ぜません。

- リポジトリ全体で重ならないようにします。
- 欠番は埋めません。
- 一度振った番号の意味は変えません。振る舞いが変わったら、新しい番号を振ります。

## 要件の書き方

見出しに要件の番号を置き、その直下に要件を 1 文で書きます。

```markdown
## REQ-014
もし設定ファイルが読めないなら、accord は探した場所を添えて起動をやめる。
```

主語は「accord は」にそろえます。書き出しは次の 5 つだけを使い、組み合わせません。

| 型 | 書き出しの形 | 使う場面 |
|---|---|---|
| 常時 | 常に、accord は〜する。 | 常に成り立つこと |
| 事象 | 〜とき、accord は〜する。 | 入力や事象への応答 |
| 状態 | 〜間、accord は〜する。 | ある状態が続く間 |
| 異常 | もし〜なら、accord は〜する。 | 望ましくない条件への応答 |
| 条件付き | 〜が有効な場合、accord は〜する。 | 設定で有効にした機能 |

1 つの番号には 1 文だけを置きます。「かつ」で 2 つの振る舞いを繋いだものも、句点で 2 文になっているものも、2 件に割ります。

## 要件に書かないこと

- 「適切に」「必要に応じて」「堅牢に」「最適化して」。どれも機械で確かめられません。
- 実装の手段。要件は外から見える振る舞いだけを述べます。どう作るかの判断は `docs/decisions/` に書きます。
- 「〜が望ましい」「可能であれば」。守らなくてよい要件は書きません。

## 要件に添える 2 項目

要件文の下に、関係するファイルと検証手順の 2 項目を書きます。

```markdown
## REQ-014
もし設定ファイルが読めないなら、accord は探した場所を添えて起動をやめる。

- 関係するファイル: `src/accord/vocabulary/settings.py`
- 検証手順: `uv run pytest tests/test_reading_settings.py -k REQ_014`
```

1 つのファイルを書き終えたら、そのファイル全体で「この要件が曖昧なせいで、実装が 2 通り以上に分かれうる箇所」を自分で点検します。見つけたら、未決の質問としてファイルの末尾に最大 3 件まで挙げます。それ以上は挙げず、先に進みません。

## 改訂したとき

要件が変わったら新しい番号を振り、古い要件には状態の行を置きます。古い要件の文は書き換えず、そのまま残します。

```markdown
## REQ-007

- status: superseded by REQ-014
```

取って代わられた要件には、テストを求めません。ただし、古い番号を名前に持つテストが残っていると検査で落ちます。

- 振る舞いが変わった改訂なら、古い番号のテストは消します。
- 文だけを直した改訂なら、テスト名の番号を新しい番号に付け替えます。

## テストの名前と実装の目印

要件を確かめるテストは、関数名を `test_REQ_014_<内容>` の形にします。1 つの要件にテストが複数あってよく、0 件は許しません。

```python
def test_REQ_014_stops_when_the_settings_file_is_unreadable():
    ...
```

要件を実現しているコードには、目印のコメントを置きます。

```python
# spec: REQ-014
if not settings_path.is_file():
    ...
```

目印は、コードを触る前に「このコードはどの要件のためにあるのか」を知るためのものです。すべての要件に目印を置くことは求めません（検査は、目印が 0 件でも合格にします）。目印の番号が、実在しない要件や取って代わられた要件を指しているときだけ落とします。

## 番号を使う場所

要件の番号を書くのは、要件のファイル・テストの名前・実装の目印・検査の出力の 4 か所だけです。利用者に返る文（ツールの戻り値、検査の結果の文、断りの理由）と、人に向けた報告には、番号ではなく中身を書きます。読み手に番号の対応表を覚えさせないためです。

## 要件を持たないルール

ルール「逆参照を書かない」だけは、要件にしません。accord が動いているときに検査して返すものではなく、層の分け方と正本の書き方で守るものだからです（`ARCHITECTURE.md` の「意図的に無いもの」）。

## 検査の走らせ方

リポジトリの直下で、次の 2 本を走らせます。

```
python3 tools/check_req_coverage_selftest.py
python3 tools/check_req_coverage.py
```

1 本目は検査そのものが壊れていないかを試し、2 本目が要件とテストと目印を突き合わせます。2 本目が見るのは次の 6 項目です。

- 要件にテストがある
- テスト名の番号が要件にある
- 取って代わられた番号のテストが残っていない
- 実装の目印が有効な要件を指す
- 番号の形と重なり
- 取って代わった先が実在する

不合格の項目の下には、番号・場所・次にすることが 1 件 1 行で出ます。この 2 本は `.github/workflows/ci.yml` の中で `pytest` より先に走ります。要件に対応するテストが無いことは、テストが落ちることより先に知る必要があるからです。
