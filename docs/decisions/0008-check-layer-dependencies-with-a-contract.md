# 層の依存を契約として書き、機械で確かめる

- 状態: 採用
- 日付: 2026-09-20

## 文脈

このリポジトリのコードは 4 つの層に分かれ、読み込みは上から下への一方向だけ、という決まりで書いてあります。決まりの中身は構造の地図に散文で書いてありますが、散文で書いた決まりは、破っても何も起きません。

逆向きの読み込みを 1 行足しても、テストは通り、動きます。層が混ざったことに気づくのは、別の用事でそのファイルを開いたときなど、ずっと後になります。層の分け方は、壊れた瞬間には何の症状も出さず、後から直すほど高くつきます。

clone した人から見ると、事情はもう 1 つ悪くなります。決まりが文書の中の文章としてしか無いので、いま書いているコードが決まりに沿っているかどうかを、機械に尋ねる手立てがありません。

## 決め

層の並びと、層をまたぐ読み込みの許し方を、リポジトリ直下の `.importlinter` に契約として書き、import-linter で確かめます。CI が `pytest` より先に走らせ、手元では `uv run lint-imports` で走らせます。

契約は 2 本です。

- **層は上から下へだけ読む。** 起動の口（`__main__`）・公開の口（`server`）・決まりの適用（`services`）・読み書き（`repository`）・型の定義（`models`）と設定（`vocabulary`）の順に並べ、逆向きの読み込みを落とします。最後の 2 つは同じ段で、互いに読み合いません。「ここに載っていない置き場を許さない」指定を付けてあるので、`src/accord/` の直下に、層に載っていないディレクトリやファイルを作った場合も落ちます。
- **設定を読むモジュールは外部のパッケージを読まない。** 名前を挙げるのは、このリポジトリが依存に宣言している 3 つです。依存を足したときは、この一覧にも足します。

層の向きについての定義は、この契約のファイルだけが持ちます。同じ定義を別の場所に書き写しません。

## 比べた選択肢

- **読み込みを調べる検査を自分で書く。** 層の向きを見るだけなら短く書けますが、読み込みの書き方によって取りこぼしが出ます。読み込む先をファイルの名前まで書いた形と、ディレクトリで止めた形とで、追い方が変わるからです。公開されている道具はどちらの形も捕まえ、落ちたときに破った契約の名前とファイルと行番号を出します。自分で書くと、塞ぐべき穴を自分で見つけ続けることになり、得るものがありません。
- **テストの中で読み込みを調べる。** テストとして書くと、層の決まりが振る舞いの検査に混ざります。落ちたときに、振る舞いが壊れたのか層が混ざったのかを、出力を読んで見分けることになります。段を分けておけば、どちらなのかが走らせる前から決まり、層が混ざっている間はテストまで進みません。
- **文章の決まりのままにする。** いまの状態です。決まりを破っても何も起きず、clone した人からは決まりの存在も見えません。この記録が塞ごうとしているもの、そのものです。

## 帰結

逆向きの読み込みと、層に載っていない置き場が、人の目ではなく CI で止まります。落ちたときの出力に、破った契約の名前と、読み込んだファイルと行番号が出るので、直す場所を探さずに済みます。決まりが公開するファイルの側にあるので、clone した人は、文書を読まなくても手元で同じ検査を走らせられます。

引き受けるものは 4 つです。

- 開発用の依存が 1 つ増えます。実行時の依存は変わりません。
- 2 本目の契約が名前を挙げるのは、依存に宣言している 3 つのパッケージだけです。それらが連れてくる間接の依存を設定のモジュールが直接読んだ場合は、この契約では捕まりません。
- 置き場を見るのは `src/accord/` の直下だけです。すでにある層のディレクトリの中に、入れ子のディレクトリを作っても落ちません。入れ子の中のファイルにも層の向きの契約は効くので、見ていないのは「入れ子を作ったこと」そのものです。
- `scripts/` の生成器は、パッケージとして導入されないため解析の対象に入りません。生成器がこのリポジトリのどのモジュールも読まないことは、機械では見ていません。
