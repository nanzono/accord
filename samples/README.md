# 同梱のサンプルについて

`data/`（経歴データの置き場）と `presentations/`（提示物の置き場）の中身は、すべて架空の人物と架空の案件である。実在の人物・会社・媒体とは関係が無い。
accord のテストと、初めて動かすときの確かめは、このサンプルの上で走る。

## 中身

見本は accord の形（`docs/data-format.md`）の実例である。accord の形はこの 1 つだけで、読み方を変える設定は無い。

| ファイル | 何の正本か |
|---|---|
| `data/vocabulary.md` | 語彙。媒体の名前・決めの適用先・機能の分類の 5 語・仮説の状態の語・公開記録の種類と役割の語 |
| `data/product/positioning.md` | 売り方の決め。1 決め 1 ブロックで積む |
| `data/product/packages.md` | パッケージ定義。パッケージでない覚え書きの節も 1 つ置いてある（型の欄を持たないので読まれない） |
| `data/product/features.md` | 機能の台帳。節の見出しが分類 |
| `data/career_master.md` | 経歴の正本。職歴の枠（深さ 3）と受託案件（深さ 4・5）を、束ねる見出しの下に入れ子で持つ |
| `data/keirekisho/daicho.md` | 職務経歴書の台帳。「案件」と「枠」で始まる見出しの節で、欄は 2 列の表 |
| `data/public_records.md` | 公開記録。1 件 1 節（深さ 2）で積む |
| `data/misekata_master.md` | 見せ方の正本。禁じた言い回しの表を持つ（型には持たない） |
| `presentations/<媒体>/` | 提示物と、媒体ごとの規約の `channel.md`。提示物でないファイルも同居する |

この正本は違反を 1 件も含まない整った状態にしてある。違反を仕込んだ形はテストが
一時的な写しの上で組み立てるので、この中身は書き換えない。

経歴の正本には、ID を持たない節（基本情報と稼働条件）と、公開不可の節の下位の節（在籍中の社内の取り組み）を
置いてある。材料の取り出しが経歴の節をすべて返すこと、ID を持たない節も返すこと、公開不可の節を
下位の節ごと落とすことを、手を入れていない見本のままで確かめるためである。どちらも職歴の枠と受託案件の
読み方の外にあるので、型としては読まれず、整合の検査の違反も増えない。

## ID の書き方

指される側の 5 つ（職歴の枠・受託案件・公開記録・機能・パッケージ）は、`- ID: teramina-delivery` の
1 行を持つ。機能は節ではなく表の 1 行なので、ID は行ではなく表の 1 列目に置く。
指す側の 6 つの欄（裏づけの節・束ねる機能・由来の節・出典の節・前面に出す束・宣言する束）と、
未反映の注記の区切りより前には、見出しや名前ではなく、この ID を書く。

| 決め | 中身 |
|---|---|
| 形 | 英小文字・数字・ハイフンで 3〜40 字、先頭と末尾は英数字（`^[a-z0-9][a-z0-9-]{1,38}[a-z0-9]$`） |
| 重なり | 5 つの型をまたいで正本全体で一意。同じ ID を 2 つの項目に付けない |
| 付け方 | 人が付ける。見出しからは自動で作らない |
| 区切り | 1 つの欄に複数書くときは半角の `/`。ID にスラッシュは入らないので取り違えない |

見出しは人が読む表示名なので、ID を変えないかぎり自由に書き換えてよい。
検査が違反を挙げるときと、書きの操作が拒否するときの候補は ID だけで返るので、そのまま渡し直せば通る。
どの節のことかは、同じ返り値の文が「候補: teramina-delivery（テラミナ物流 配送データの置き場づくり）」
のように表示名を添えて示す。

## 検査が読む欄の書き方

整合の検査（`check_consistency`）は、正本の次の欄を読む。欄の名前も区切りも、下の形で書く。

| 欄 | どのファイルのどこ | 書き方 |
|---|---|---|
| 最終更新 | `product/packages.md` の各節 | `- 最終更新: 2026-09-12`。この日が、その束を前面に出した決めの日付より古いと鮮度の違反になる |
| 例外 | `product/positioning.md` の各ブロック | `- 例外: なし`、または `- 例外: presentations/<媒体>/<ファイル名> — 理由`。1 行 1 件で、行を足せば何件でも書ける。ここに書いた提示物は、宣言と看板の一致の検査を飛ばす |
| 宣言する束 | 提示物の先頭 | `- 宣言する束: <パッケージの ID>`。その媒体に適用される決めの看板と違うと違反になる |
| 未反映の注記 | 提示物の先頭 | `- 未反映の注記: なし`、または `- 未反映の注記: <受託案件の ID> — 覚え書き`。区切りより前が、その事実の入る先の節の ID。指す節が無ければ違反、注記が残っていること自体は断りとして報告に出る |
| 出典の節 | `keirekisho/daicho.md` の各ブロックと、提示物の先頭（任意） | 台帳の案件は `- 出典の節: <受託案件の ID>`、在籍職歴の枠は `- 出典の節: <職歴の枠の ID> / <職歴の枠の ID>`。指す先の型の ID に限り、公開可の節に限る。提示物は `- 出典の節: <職歴の枠か受託案件の ID>` で、宣言した提示物だけ写しの鮮度を見る |
| 出典の指紋 | `keirekisho/daicho.md` の各ブロックと、出典の節を宣言した提示物 | `- 出典の指紋: <ID>=<指紋>`。出典の節に書いた ID ごとに、写したときのその節の本文の指紋を書く。いまの本文の指紋と違うか、組が無いと写しの鮮度の違反になり、違反の文が書くべき行を返す |
| URL | `public_records.md` の各ブロック | `- URL: https://example.com/events/report/spring-meetup/`、または `- URL: なし`。提示物の本文に貼った URL は、同じホストのものだけがここと突き合わされる。経路の書き方だけが違うものも違反になる |
| 由来の節 | `public_records.md` の各ブロック | `- 由来の節: <職歴の枠か受託案件の ID>`、または `- 由来の節: なし`。書いた ID が実在しないと違反になる |

区切りの `—` は全角のダッシュ 1 文字である。日付は `2026-09-12` の形で書く。

## 書きの操作が書く形

決めの登記（`record_positioning`）とパッケージの改訂（`revise_package`）は、正本を下の形で書く。
手で書き足すときも同じ形にしておくと、読み戻しで落ちない。

事実の登記（`record_fact`）は、経歴の正本の節の本文の末尾（下位の見出しの前）に、
「- 事実の文（2026-10-01、出所: 確かめた先）」の 1 行を足す。節の書き換え（`revise_section`）は、
節の見出しの行と下位の節を残して、本文だけを置き換える。

**売り方の決め（`product/positioning.md`）。** 1 決め 1 ブロックで、末尾に積む。過去のブロックは書き換えない。

```
## 2026-09-16 全体

- 日付: 2026-09-16
- 適用範囲: 全体
- 前面に出す束: requirements-and-progress
- 根拠: 直近 3 件の引き合いが、作る前の整理に集中していたため。
- 例外: なし
```

見出しは「日付 適用範囲」の形にする。適用範囲は媒体の名前か「全体」で、媒体の名前は語彙の
「媒体」の綴りに限る。必須の欄は日付・適用範囲・前面に出す束・根拠の 4 つで、1 つでも欠けると
そのブロックは決めとして読まれず、検査の断りに「どのブロックのどの欄が無いか」が出る。
前面に出す束は `product/packages.md` にある節の ID に限る。例外は 1 行 1 件で、行を足せば何件でも書ける。
根拠のように文が長く複数行にしたい欄は、同じラベルの行を続けて書く（`- 根拠: 1 行目` の次の行に
また `- 根拠: 2 行目`）。読み戻すときは、同じラベルの行を改行でつないで 1 つの値に戻す。

**パッケージ定義（`product/packages.md`）。** 1 パッケージ 1 節。改訂は積まずに、その節を丸ごと差し替える。

```
## 要件定義と進行管理

- ID: requirements-and-progress
- 最終更新: 2026-09-16
- 想定買い手: 専任の進行役を置けない、従業員 100 名前後の会社の事業責任者
- 仮説の状態: 検証中
- 判定根拠: 受注 2 件がどちらも継続している。
- 出典: career_master.md の「ナギサ書房 刊行計画の進行管理」
- 崩れる条件: 進行役を自社で採用できる規模の会社が、相手の中心になったとき
- 束ねる機能: requirements-forum / plan-from-decisions
```

節の見出しがパッケージの表示名になり、決めと提示物は「ID」の行の値でこの束を指す。
最終更新は改訂の操作が今日の日付に進めるので、手で書く必要は無い
（手で書くときは、その束を前面に出した決めの日付以降にする）。仮説の状態は語彙の
「パッケージの仮説の状態」の語に限る。束ねる機能は `product/features.md` にある機能の ID に限り、`/` で区切る。
判定根拠・出典・崩れる条件は任意で、改訂の入力に無ければ前の節の値がそのまま残り、残したことが警告に出る。

**機能の台帳（`product/features.md`）。** 機能の登記（`register_capability`）は、分類の節の表に 1 行足す。
その分類の節がまだ無ければ、節と表の見出しごと作って足す。表の列は「ID、機能名、説明、裏づけの節」の
並びで、1 列目の ID をパッケージが指す。

**公開記録（`public_records.md`）。** 公開記録の登記（`register_public_record`）は、1 件 1 ブロックで
末尾に積む。過去のブロックは書き換えない。

```
## 刊行計画の進め方を話した勉強会の発表

- ID: meetup-talk-publishing
- 種類: 登壇
- 日付: 2025-11-08
- URL: https://example.com/events/report/spring-meetup/
- 発行元か主催: 出版まわりの仕事を持ち寄る勉強会（架空の催し）
- 役割: 登壇者
- 由来の節: nagisa-publishing
- 出所: 発表の資料と、主催が出した開催の記録
```

節の見出しが公開記録の表示名になり、機能の裏づけの節は「ID」の行の値でこの 1 件を指す。
必須の欄は ID・名前・種類・日付・発行元か主催・役割の 6 つで、種類と役割は語彙の「公開記録の種類」と
「公開記録の役割」の語に限る。日付は `2020-03-10` の形で書き、月までしか分からないときは
`2020-03`、年だけなら `2020` と書く。URL・由来の節・出所は任意で、値が無いときは「なし」と書く。

## 見せ方の正本と媒体の規約の書き方

`misekata_master.md` と、提示物の置き場の `<媒体>/channel.md` は、材料の取り出し（`assemble_material`）だけが読む。
accord はこの中身を型として持たない。見せ方の良し悪しは機械で判定しないので、読んで渡すところで止める。

- `misekata_master.md` の、見出しが「本人が禁じた言い回し」の節（深さは問わず、末尾の括弧書きは見ない）の
  最初の表の 1 列目が、どの媒体でも同じ「禁じた言い回し」として返る。
- `<媒体>/channel.md` の箇条書きが、その媒体の「媒体の規約」として返る。箇条書きでない行は読み飛ばす。
  ファイルが無い媒体の規約は空で、そのことが警告に出る。
