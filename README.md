# accord

自分の経歴や売り込み方を書いた Markdown と、そこから作るプロフィール・応募文・職務経歴書が、いつの間にか食い違うのを防ぐ、手元で動く MCP サーバーです。

> **English:** accord is a local MCP server that keeps one source of truth (what you can do, what you have done, how you sell it) consistent with everything derived from it (profiles, applications, résumés). Run it with `uv sync`, `uv run pytest`, `uv run accord --list`. The rest of this document is written in Japanese.

## 要するに

フリーランスや転職活動で、自分の経歴と売り込み方を Markdown に書きためている人のための道具です。「いま何を前面に出して売るか」（この README ではこれを売り込み方と呼びます。ツール名では positioning）を日付つきで記録しておくと、古い売り文句のまま残っているプロフィールや、実在しない実績を根拠にした文章を、書く前・出す前に機械が指摘します。

使い方は 2 通りです。Claude などの AI から MCP（AI が外部ツールを呼ぶための共通の仕組み）経由で呼ぶのが本来の使い方で、AI が文章を書くときに材料を取り出し、書く前に食い違いを確かめます。人が手で確かめたいときは、Python から同じ機能を直接呼べます（下の「動くとこうなる」）。

## どんなときに困るか

自分の仕事を自分で売る人は、たいてい 3 種類のファイルを持っています。

- 何ができるか（スキルや提供できるサービスの一覧）
- 何をしてきたか（職歴や案件の実績）
- どう売るか（どのサービスを前面に出すか、誰向けに書くか）

そこからプロフィールや応募文や職務経歴書を書きます。困るのは、売り込み方を変えたときです。「今月から PM の仕事を前面に出す」と決めても、その決定は会話の中で終わってどこにも残りません。結果として、サービスの説明が 1 か月前のまま放置されたり、もう売りにしていないサービスを名乗ったプロフィールが何枚も残ったりします。ルールとしては書いてあるのに、文章を書くその瞬間には思い出せません。

## accord がやること

accord は、そのルールを「読んで覚えておくもの」から「書く瞬間に返ってくるもの」に変えます。文章そのものは書きません。書くのは人か AI で、accord がするのは材料を渡すことと、食い違いをその場で止めることです。

| ツール | 何をするか |
|---|---|
| `get_positioning` | いまの売り込み方（何を前面に出しているか）を返す。まだ記録が無ければ「先に記録してください」と返す |
| `assemble_material` | 媒体（転職サイトやマッチングサービス）向けの文章を書くための材料をまとめて返す。中身は、いまの売り込み方、前面に出すサービスの説明、その根拠になる実績の本文、その媒体の書き方の決まり（文字数など）、使わないと決めた言い回し。公開できない実績は除き、除いたことを知らせる |
| `record_positioning` | 「今日から何を前面に出すか」を日付つきで記録する。必須の項目が欠けていれば、欠けた項目と書き方の例を返して書き込まない |
| `register_capability` | できることの一覧に 1 行足す。根拠にした実績の見出しが実在しなければ、近い見出しを候補として返して書き込まない |
| `revise_package` | サービスの組み合わせ（パッケージ）の説明を更新し、更新日を進める。一覧に無いスキルを組み合わせに入れると、近い名前を候補として返して書き込まない |
| `check_consistency` | 全ファイルをルールに照らし、食い違いを「どのファイルのどこを、何に合わせるか」つきで一覧にする |
| 資源 `accord://ontology` | データの型とルールの定義を、AI が読める形で返す。AI がセッションの最初に読んで前提を揃えるためのもので、利用者が何かする必要はない |

書き込む 3 つのツールは、ルールに通った入力だけを書き、通らない入力は書かずに「次に何をすればよいか」を返します。読むだけのツールと検査は、ファイルを一切変えません。

## 動かしてみる

Python 3.12 以上と [uv](https://docs.astral.sh/uv/) が必要です。架空の人物と架空の案件で作ったサンプルデータを同梱しているので、設定なしでそのまま動きます。

```
uv sync                # 依存パッケージを入れる
uv run pytest          # テストが通ることを確かめる
uv run accord --list   # ツール 6 つと資源 1 つの名前を表示する
```

引数なしで `uv run accord` を実行すると、標準入出力で MCP サーバーとして起動します。画面には何も出ませんが、それで正常です（AI 側からの接続を待っています）。ネットワークは使いません。

## 動くとこうなる

サンプルデータのプロフィール 1 枚を、わざと古いサービス名を名乗った状態にして検査を呼ぶと、次の 1 件が返ります（出力の「看板」は前面に出しているサービス、「束」はサービスの組み合わせ、「提示物」はプロフィールなどの文章のことです）。

```json
{
  "constraint": "提示物の宣言と看板の一致",
  "file": "presentations/tsukikusa/profile.md",
  "location": "「宣言する束」の行",
  "expected": "いまの看板は「要件定義と進行管理」（2026-09-10 の決め・適用範囲 全体）で、この文面は「データの置き場づくり」を名乗っている。宣言する束を看板の名前に書き換える。この文面だけ合わせない理由があるなら、決めの「例外」欄にこのファイル名と理由を書く。",
  "candidates": ["要件定義と進行管理"]
}
```

日付を書き忘れて売り込み方を記録しようとすると、書き込まずに次が返ります。

```json
{
  "accepted": false,
  "rejection": {
    "constraint": "決めの必須欄",
    "reason": "決めの必須の欄「日付」が無い。欄のそろわない決めは、いまの看板として読めない。",
    "next_action": {
      "operation": "record_positioning",
      "missing_fields": ["日付"],
      "example": "- 日付: 2026-09-16（この決めを決めた日。パッケージ定義の鮮度は、この日付と比べて判定する。）"
    }
  }
}
```

Python から直接呼ぶなら次の形です。

```python
from pathlib import Path
from accord.vocabulary.settings import load_settings
from accord.services.consistency import ConsistencyService

settings = load_settings(Path("samples/accord.toml"))
report = ConsistencyService(settings).inspect()   # 範囲を省くと全体
for v in report.violations:
    print(v.constraint, v.file, v.expected)
```

## 自分のデータで使う

`samples/accord.toml` をコピーして書き換え、起動時に指定します。

```
uv run accord --config /path/to/your/accord.toml
```

設定ファイルに書くのは、Markdown の置き場と、自分の言葉（媒体の名前、スキルの分類、サービスの状態を表す語。たとえば「仮説のみ・検証中・実績あり」）です。Markdown の形はサンプルを見るのが早く、たとえば売り込み方の記録は次の形です。

```markdown
## 2026-09-10 全体

- 日付: 2026-09-10
- 適用範囲: 全体
- 前面に出す束: 要件定義と進行管理
- 根拠: 直近 3 件の引き合いが、作る前の整理と、決まったことを進める役の不在に集中していたため。
- 例外: なし
```

自分の Markdown の書き方がサンプルと違っていても、見出しの深さ、項目を箇条書きで書くか表で書くか、項目名の言い換え、を設定の `[reading]` の節で指定すれば、ファイルを書き換えずに読めます。指定できる範囲と書き方は `samples/README.md` にあります。

Claude Code から使うときは、プロジェクトの `.mcp.json` に次のように書きます。

```json
{
  "mcpServers": {
    "accord": {
      "command": "uvx",
      "args": ["--from", "/path/to/accord", "accord", "--config", "/path/to/your/accord.toml"]
    }
  }
}
```

## 中身の作り

- **4 つの層に分けています。** MCP のツールを公開する薄い層（`server/`）、ルールを適用する層（`services/`）、Markdown を読み書きする層（`repository/`）、Markdown ファイルそのものです。依存は上から下への一方向だけで、Markdown の書き方を知っているのは `repository/` だけです。
- **型とルールの定義は YAML に置いています。** `src/accord/ontology.yaml` が、データの型 7 つ（売り込み方・パッケージ・スキル・職歴・案件・文章・職務経歴書の台帳）と、型どうしの関係、ルール 7 つ（たとえば「文章が名乗るサービスは、いまの売り込み方と一致する」「実績の見出しは実在する」）を定めます。Pydantic（Python の型検証ライブラリ）のモデルはそこから自動生成し、`scripts/generate_models.py --check` で定義とのずれを検査します。ルールを 1 か所に書いておくと、同じルールが「書くときは拒否、読むときは警告、検査では一覧」という 3 つの形で現れても、定義は 1 つで済みます。
- **自分の言葉と書き方は設定に置いています。** 媒体名やスキルの分類のような、人によって違う言葉は型に埋め込まず設定ファイルから読みます。特定の人や会社の言葉を型に埋め込むと、型の定義ごと公開できなくなるからです。
- **拒否は例外ではなく戻り値です。** ルールに反する入力は、エラーを投げるのではなく「受け付けなかった理由」と「次に何をすればよいか」を持つ値として返します。返ってきた候補をそのまま渡し直せば通る形にしてあります。
- **公開の境界を機械で守っています。** このリポジトリに出てくる人物・会社・媒体の名前はすべて架空で、実在しないことを確かめた記録は `samples/README.md` にあります。作者の実データの語（クライアント名や単価）が入っていないことは、コミットのたびに作者の手元で、語の一覧と差分を突き合わせる検査で確かめています（語の一覧と検査はこのリポジトリには含めていません）。

```
src/accord/ontology.yaml   型・関係・ルールの定義（正本）
src/accord/server/         MCP のツールを公開する層
src/accord/services/       ルールを適用する層
src/accord/repository/     Markdown の読み書き
src/accord/models/         ontology.yaml から生成した型のコードと、戻り値の型
src/accord/vocabulary/     設定ファイルの読み込み
scripts/generate_models.py ontology.yaml から models/ の型のコードを生成する
samples/                   架空の設定とサンプルデータ
tests/                     受け入れ条件のテスト
```

## 作り方とライセンス

設計の文書を先に固め、受け入れ条件を仕様書として実装より先にコミットし、実装した側とは別の担当が仕様書だけを見て確認する、という手順で作りました。実装と確認の多くは AI（Claude Code）に任せ、設計の判断・仕様の確定・確認結果の検証・コミットは作者が行っています。
